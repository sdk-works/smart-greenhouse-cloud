# 运维工具与观测修正 · 2026-10-23

## 1. `dbq.sh` 黑名单误伤：已修

**旧版问题**：用**子串**黑名单（`*create*` / `*update*` / `*delete*` …），
于是 `select created_at ...`、`select updated_at ...` 这种最常见的查询被判成写操作。

```
$ dbq.sh.bak-20261023-0150 "select created_at from telemetry order by created_at desc limit 2"
REJECTED: mutating keyword detected
```

**修法**：改成**按语句动词**判断 —— 动词必须出现在**语句开头**（或 `;` 之后），
且后面跟空白/行尾。所以 `created_at`（`create` 后面是 `d`）不会命中。

```
$ dbq.sh "select created_at from telemetry order by created_at desc limit 2"
          created_at
-------------------------------
 2026-10-23 08:54:18.978728+08
 2026-10-23 08:53:18.978728+08   ←（实际输出第二行 08:53:18.971437）
(2 rows)

$ dbq.sh "update telemetry set id='x'"
REJECTED: 只允许只读语句（SELECT / WITH / \d / SHOW / EXPLAIN / TABLE / DESCRIBE）

$ dbq.sh "select 1; drop table telemetry"
REJECTED: 检测到写操作语句动词
```

- 新版：`/opt/greenhouse-nightly/dbq.sh`（旧版备份 `dbq.sh.bak-20261023-0150`），
  源码进 git：`worktree/scripts/dbq.sh`。
- 自测：`tests/test_dbq_guard.py` **4 passed**，两头都钉住：
  只读含 `created_at`/`updated_at` 的查询**必须放行**；
  insert/update/delete/drop/alter/truncate/create/grant/vacuum/copy **必须拒绝**；
  `select 1; drop table x` 多语句注入**必须拒绝**（只判首句是不够的）。

## 2. 断流事件记录：`scripts/outage_watch.py`

判据：**连续 N 条相邻间隔 > 2×记录周期 → 记一次断流事件**。
单条超阈值不算（网络抖动、补传、服务端重启都会造成一次长间隔）；
另外单独判"**进行中**"：`now - 最后一条 > 2×周期`，不必等够 N 条 ——
因为设备停传后不会再有"下一条间隔"了，这正是 08:55 那次的情况。

**只记录，不告警到人**：落盘是本地 JSONL（默认
`/opt/greenhouse-nightly/logs/outage-events.jsonl`），不写业务库、不发消息、不动设备。
同一 `(device, kind, started_at)` 不会重复记。

生产只读实测（`--no-write`，不落盘）：

```
$ python3 scripts/outage_watch.py --db-url "$DATABASE_SYNC_URL" --device JY001 --no-write
设备=JY001  窗口=48h  样本=6989 条  周期=60.0s  阈值=120.0s  连续阈值=3 条
最后一条：2026-10-23 08:54:18.978728+08:00
  [进行中] 自 2026-10-23T08:54:18.978728+08:00 起静默 54999.2s （阈值 120.0s）
本次新记 0 条 → /opt/greenhouse-nightly/logs/outage-events.jsonl
```

测试：`tests/test_outage_watch.py` **8 passed**
（无缺口不报 / 单条长间隔不报 / 连续 N 条报 ended / 进行中靠 now−last 报 ongoing /
无数据返回空 / 落盘幂等 / 坏行跳过 / 测试库真跑一次并同时看出 ended 与 ongoing）。

> 建议挂 cron（例如每 10 分钟一次）。**本次没有挂 cron** —— 改生产 crontab 属于需要
> 人批准的范围。命令：
> `*/10 * * * * /opt/greenhouse/venv/bin/python /opt/greenhouse-nightly/worktree/scripts/outage_watch.py --db-url "<DSN>" --device JY001`

## 3. `--reconcile` 稳定指标：已补 `重复` 与显式 `reread`

改前 `reconcile-latest.json` 只有 `{ts, groups, expected, missing}`：
没有"重复"，也没有 `reread`（只能在人读的摘要里看到，机器读不到）。

改后（`/opt/greenhouse-nightly/observer.py`，备份 `observer.py.bak-20261023-0210`）：

```
$ python3 observer.py --reconcile
==============================================================
完整性对账 2026-10-24 00:12:31
组数 30 / 应有 19049 条 / 缺 0 条 / 重复 0 条 / 主游标重读 0（应为 0）
...
(无缺失)

$ cat logs/reconcile-latest.json
{"ts": 1792771950, "groups": 30, "expected": 19049, "missing": 0, "duplicate": 0,
 "reread": 0, "self_check": {"reread_is_zero": true, "duplicate_resolved": true}}
```

口径说明：
- `expected` 应有 / `missing` 缺失 / `duplicate` 重复（同一 `msg_id` 在 `telemetry` 里出现多次）；
- **`reread` 必须显式为 0**，不是"没输出"。查不出来时 `duplicate` 记 **-1**
  （-1 ≠ 0，`self_check.duplicate_resolved=false`），避免把"没查"当成"没有重复"。
- 摘要文件仍**不写 state**：对账与实时观测由不同 cron 触发，写同一个 state 会互相覆盖游标。
