## 3. `keepalive=0` 为什么会造出"假在线"

1. MQTT 的 keepalive 是**客户端声明**的心跳周期。设备 CONNECT 时填 `0`，语义是"**不启用心跳**"。
2. EMQX 因此：既不向设备发 `PINGREQ`，也不期望设备发 `PINGREQ`，**永远不会**因空闲判定该连接超时（默认 15s 超时规则对 keepalive=0 的会话不生效）。
3. 于是连接的存活只剩 TCP 层。而 TCP **只有在有数据要发时才会发现对端消失**：
   - 08:54:19 云端发完最后一条 ACK，`bytes_acked == bytes_sent`，`Send-Q=0` → 对端当时**确实还在 ACK**；
   - 08:55:18 之后云端**没有任何要发的东西**（ACK 只在收到上行时才产生），也就**没有任何写操作会失败**；
   - Linux 默认 `tcp_keepalive_time=7200s` 且看起来未启用 SO_KEEPALIVE（15 小时未断），TCP 层也不会主动探测。
4. 结果：**"connected=true" 只代表"EMQX 没收到过 FIN/RST"，不代表设备还活着**。
   设备掉电时 TCP 来不及发 FIN，连接就会像这样永远挂着。

> 判据：`bytes_sent == bytes_acked && Send-Q == 0` 只能说明"截至最后一次交互对端还 ACK 过"，
> **不能**证明现在还活着。要证明活着，必须有持续的**上行**数据或显式心跳。

### 4.1 一个能一锤定音的判据

设备恢复后看**第一条**遥测的 `msg_id`：

```bash
# 生产只读
sudo -n -u postgres psql -d greenhouse -At -c \
  "select msg_id, created_at from telemetry order by created_at desc limit 3;"
```

- `JY001/32/1` 之类（**boot 变了、seq 归 1**）→ 设备**重启过** → 指向 **A 供电** 或看门狗复位；
- `JY001/31/923`（**boot 不变、seq 续上**）→ MCU **没重启**，是通信侧（**B 网络**）或采集任务（**C 固件**）；
- 若 boot 31 seq 923 之后又出现跳号 → 队列补传，说明中断期间 MCU 一直在采样并缓存（指向 **B**）。

## 5. 现场排查步骤（用户到现场，不接调试串口）

按顺序做，每步都记结果：

1. **看 DTU 指示灯**（最关键，先拍照）
   - PWR 灭 → **A 供电**：查适配器、接线端子、市电、空开。
   - PWR 亮 / NET 灭或慢闪 → **B 网络**：查天线、SIM 欠费、信号强度、运营商。
   - PWR 亮 / NET 常亮 / 数据灯不闪 → **C 固件**：MCU 侧问题。
2. **看 MCU/传感器板指示灯**：运行心跳灯是否还在闪。不闪 → MCU 死机或掉电。
3. **断电重启一次**（现场可做，无需云端配合），记下重启时刻。
4. **云端核对恢复情况**（只读）：
   ```bash
   sudo -n emqx ctl clients list | grep 02501026081300004386   # 看 connected_at 是否刷新
   sudo -n -u postgres psql -d greenhouse -At -c "select msg_id, created_at from telemetry order by created_at desc limit 3;"
   ```
5. 把第 3 步的重启时刻与第 4 步的 `boot_id` 对照，套用 §4.1 判据。
