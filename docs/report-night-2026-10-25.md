### 2.1 断流监测：回看窗口内 0 条样本 ⇒ 状态退化成「正常运行」

**复跑时看到的现象**（2026-10-25 23:35，生产只读）：

```
$ python3 scripts/outage_watch.py --db-url "$DATABASE_SYNC_URL" --device JY001 --period 60
设备=JY001  窗口=48h  样本=0 条  周期=60.0s  阈值=120.0s  连续阈值=3 条
最后一条：（无数据）
当前状态：正常运行   设备离线=True  数据过期=True  需通知=False      ← 设备已静默 62 小时
  计划停机：用户 / 主动断电（计划停机，非故障）  2026-10-23T08:54:18+08:00 → 2026-10-26T18:00:00+08:00
断流事件：无
```

**根因**：`find_outages` 只看 `--lookback-hours`（默认 48h）窗口内的样本，
窗口内一条都没有 ⇒ 返回空 ⇒ `summarize` 取不到 `ongoing` 事件 ⇒ 顶层状态退回 `ok`。
**设备离线越久，状态看起来越"正常"** —— 断的方向完全反了。
（`device_offline=True` / `data_stale=True` 是对的，但顶层 `state` 是错的。）

**修法**：另查该设备**全表末条**作为锚点 `anchor`：

| 情况 | 行为 |
|---|---|
| 窗口内有样本 | `anchor` = 窗口内末条，与原行为完全一致 |
| 窗口内 0 条、全表有末条 | 据此判"进行中静默"，起点如实取该时刻 |
| 全表一条都没有 | `anchor=None`，**不编造** `last_seen` / 静默时长，仍为 `ok` |

**修后同一时刻三种场景实测**（生产只读，`--no-write`）：

```
=== 有维护窗口且在窗口内（当前真实状态）===

当前状态：计划停机   设备离线=True  数据过期=True  需通知=False
  [计划停机] 自 2026-10-23T08:54:18.978728+08:00 起静默 225675.1s （阈值 120.0s）

=== 窗口已过期仍无数据（这就是 10-26 18:00 之后的样子）===
当前状态：计划停机超期未恢复   需通知=True
  [计划停机超期未恢复] 超出计划恢复时间 106545.5s，需人工确认
```

### 2.2 部署演练：WS 路由检查是一条永不生效的 grep

`deploy_rehearsal.sh` 第 3 步原来是：

```bash
curl -s "http://127.0.0.1:$PORT/openapi.json" | grep -o '"/api/v1/ws/realtime"'
```

而 **FastAPI 的 OpenAPI schema 不包含 WebSocket 路由**（`docs/openapi.yaml` 里搜不到任何 `/ws/`，
已核实）。所以这条 grep **永远匹配不到**，输出空行，脚本又不因它失败 —— 演练报告里
"WS 路由是否在"这一栏一直是空白，被当成"没输出=没问题"。

**改成真实握手**：新增 `scripts/ws_route_probe.py`，不带 token 真连一次
`/api/v1/ws/realtime`，期望服务端 accept 后 `close(4401)`。
该分支在 token 为空时 `_resolve_user` 直接返回 `None`、**不查 redis**，因此不依赖 6399。

```

WS 路由握手退出码=0
```
